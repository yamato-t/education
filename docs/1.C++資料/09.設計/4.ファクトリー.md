# **ファクトリパターン**

---

## **ファクトリパターンとは**

ファクトリパターンとは、オブジェクトの生成処理を専用の場所に集約し、  
<span style ="color: red;">**呼び出し側が生成するクラスの詳細を知らなくて済むようにする**</span>設計パターンの総称。  

「ファクトリ（工場）」という名の通り、  
何を作るかを指示するだけで、作り方はファクトリに任せる。  

ファクトリパターンには段階的に三つのバリエーションがある。  

| パターン名 | 概要 | 複雑さ |
|---|---|---|
| ファクトリ | 生成処理を一か所にまとめる | 低 |
| ファクトリメソッド | 生成処理をサブクラスに委ねる | 中 |
| アブストラクトファクトリ | 関連するオブジェクト群をまとめて生成する | 高 |

---

## **ファクトリ**

### **概要**

最も基本的な形。  
生成処理を一つのクラスに集約するだけのシンプルな仕組み。  

### **なぜ必要か**

敵キャラを生成する処理が各所に散らばっている場合を考える。  
ステージ毎に敵の生成処理を作成する。

```c++
// ステージ１で敵を生成する
void createEnemyInStage1() {
    Enemy* e1 = new Slime();
    Enemy* e2 = new Dragon();
    Enemy* e3 = new Slime();
}

// ステージ２で敵を生成する
void createEnemyInStage2() {
    Enemy* e1 = new Slime();
    Enemy* e2 = new Dragon();
    Enemy* e3 = new Slime();
    Enemy* e4 = new Skeleton();
}
```

この状態の時、仮に `Slime` のクラス名が変わってしまうと、  
`new Slime()` と記述しているすべての箇所を変更しなければならない。  
変更箇所が多く、漏れも発生しやすい。  

### **実装例**

```c++
class EnemyFactory {
public:
    // 種類を渡すだけで適切な敵を生成して返す
    static std::unique_ptr<Enemy> create(std::string_view type) {
        if (type == "enemy1") return std::make_unique<Slime>();
        if (type == "enemy2") return std::make_unique<Dragon>();
        if (type == "enemy3") return std::make_unique<Goblin>();
        if (type == "enemy4") return std::make_unique<Skeleton>();

        return nullptr;
    }
};

// 呼び出し側は type を渡すだけでよい
auto enemy = EnemyFactory::create("enemy1");
```

生成処理が `EnemyFactory` 一か所に集まるため、  
新しい敵を追加するときや、クラス名が変わった場合も修正箇所が明確になる。

## **ファクトリメソッド**

### **概要**

「どのオブジェクトを生成するか」の決定を派生クラスに委ねる。  
<span style ="color: red;">**親クラスは生成処理の枠組みだけを定義し、具体的な生成は派生クラスが担う。**</span>  

### **なぜ必要か**

ステージの種類によって出現する敵が異なる場合を考える。  
ファクトリに分岐を増やし続けると肥大化していく。  

```c++
// ファクトリが膨れ上がった例
std::unique_ptr<Enemy> create(std::string_view stage, std::string_view type) {
    if (stage == "forest") {
        if (type == "normal") return std::make_unique<Goblin>();
        if (type == "boss")   return std::make_unique<Dragon>();
    }
    else if (stage == "castle") {
        if (type == "normal") return std::make_unique<Knight>();
        if (type == "boss")   return std::make_unique<King>();
    }
    // ステージが増えるほど分岐が膨れ上がる…

    return nullptr;
}
```

大量のステージと敵種類が追加されてしまえば、  
いくら関数化していても分岐が多くて見にくい上に、間違えやすくなってしまう。


### **実装例**

まずは敵生成の流れを持つクラスを用意する。  

```c++
// 敵生成基底クラス
// 生成の枠組みだけを定義する
class EnemySpawner {
public:
	EnemySpawner() = default;
	virtual ~EnemySpawner() = default;

	// 敵の生成と初期化まで行う流れを定義
	std::unique_ptr<Enemy> spawnEnemy() {
		auto enemy = createEnemy(); // 生成はサブクラスに任せる
		enemy->initialize();
		return enemy;
	}

	// ボスの生成と初期化まで行う流れを定義
	std::unique_ptr<Enemy> spawnBoss() {
		auto boss = createBoss(); // 生成はサブクラスに任せる
		boss->initialize();
		return boss;
	}

protected:
	// 派生先が具体的な生成を担う
	virtual std::unique_ptr<Enemy> createEnemy() = 0;
	virtual std::unique_ptr<Enemy> createBoss() = 0;
};
```

ステージに合わせた具体的な敵の生成は、  
派生先で実装する。


```c++
// 森の敵生成クラス
class ForestEnemySpawner : public EnemySpawner {
protected:
	// 森の敵はゴブリン（具体的な生成を実装する）
	std::unique_ptr<Enemy> createEnemy() override {
		return std::make_unique<Goblin>();
	}

	// 森のボスはドラゴン（具体的な生成を実装する）
	std::unique_ptr<Enemy> createBoss() override {
		return std::make_unique<Dragon>();
	}
};

// 城の敵生成クラス
class CastleEnemySpawner : public EnemySpawner {
protected:
	// 城の敵はナイト（具体的な生成を実装する）
	std::unique_ptr<Enemy> createEnemy() override {
		return std::make_unique<Knight>();
	}

	// 城のボスはキング（具体的な生成を実装する）
	std::unique_ptr<Enemy> createBoss() override {
		return std::make_unique<King>();
	}
};
```

呼び出しの際に、利用する Spawner クラスを変更すれば、  
生成される敵を纏めて切り替える事が出来る。

```c++
// 呼び出し側は Spawner の種類だけを意識する
std::unique_ptr<EnemySpawner> spawner{};

// 森の敵生成クラスの生成
{
    spawner = std::make_unique<ForestEnemySpawner>();
    // ゴブリンとドラゴンが生成される
    auto enemy = spawner->spawnEnemy();
    auto boss = spawner->spawnBoss();
}

// 城の敵生成クラスの生成
{
    spawner = std::make_unique<CastleEnemySpawner>();
    // ナイトとキングが生成される
    auto enemy = spawner->spawnEnemy();
    auto boss = spawner->spawnBoss();
}
```

新しいステージを追加するときは `EnemySpawner` を継承した  
新しいクラスを作るだけでよく、既存コードへの影響がない。

## **アブストラクトファクトリ**

### **概要**

「関連するオブジェクトの群（各部品）」をまとめて生成する。  
<span style ="color: red;">**生成されるオブジェクト同士の組み合わせの一貫性を保証する**</span>のが目的。  

### **なぜ必要か**

UIのテーマ切り替えを考える。  
ダークテーマとライトテーマでは、ボタン・アイコン・背景が  
セットで切り替わらなければならない。  

```c++
// テーマの切り替えを個別に管理するとミスが起きやすい
Button*     btn  = new DarkButton();
Icon*       icon = new LightIcon();   // ← ライトとダークが混在してしまう
Background* bg   = new DarkBackground();
```

### **実装例**

まずは各部品の基底クラスと、テーマ毎の派生クラスを用意する。

```c++
// 生成する部品のインターフェース（内容は省略）
// 基底クラスのポインタで破棄するため、仮想デストラクタを持たせる
class Button     { public: virtual ~Button() = default; };
class Icon       { public: virtual ~Icon() = default; };
class Background { public: virtual ~Background() = default; };

// ダークテーマ用の部品群
class DarkButton : public Button {};
class DarkIcon : public Icon {};
class DarkBackground : public Background {};

// ライトテーマ用の部品群
class LightButton : public Button {};
class LightIcon : public Icon {};
class LightBackground : public Background {};
```

次に、関連する部品を生成するファクトリ基底クラスを用意する。

```c++
// ファクトリのインターフェース
// 関連する部品の生成処理をまとめて定義する
class UIFactory {
public:
	virtual ~UIFactory() = default;

	virtual std::unique_ptr<Button>		createButton() = 0;
	virtual std::unique_ptr<Icon>		createIcon() = 0;
	virtual std::unique_ptr<Background> createBackground() = 0;
};
```

ファクトリクラスを継承し、  
テーマ毎に生成する部品を具体化する。

```c++
// ダークテーマ用ファクトリ
// 必ずダーク系で揃う
class DarkUIFactory : public UIFactory {
public:
	std::unique_ptr<Button>		createButton()     override { return std::make_unique<DarkButton>(); }
	std::unique_ptr<Icon>		createIcon()       override { return std::make_unique<DarkIcon>(); }
	std::unique_ptr<Background> createBackground() override { return std::make_unique<DarkBackground>(); }
};

// ライトテーマ用ファクトリ
// 必ずライト系で揃う
class LightUIFactory : public UIFactory {
public:
	std::unique_ptr<Button>		createButton()     override { return std::make_unique<LightButton>(); }
	std::unique_ptr<Icon>		createIcon()       override { return std::make_unique<LightIcon>(); }
	std::unique_ptr<Background> createBackground() override { return std::make_unique<LightBackground>(); }
};

```

呼び出し側はファクトリを差し替えるだけでテーマ全体が切り替わる。

```c++
// UIFactoryのポインタを保持するスマートポインタ
std::unique_ptr<UIFactory> factory{};

// ダークテーマのUIを生成する場合
{
    factory = std::make_unique<DarkUIFactory>();
    auto btn = factory->createButton();
    auto ico = factory->createIcon();
    auto bg  = factory->createBackground();
}

// ライトテーマのUIを生成する場合
{
    factory = std::make_unique<LightUIFactory>();
    auto btn = factory->createButton();
    auto ico = factory->createIcon();
    auto bg  = factory->createBackground();
}
```

## **三つのパターンの使い分け**

| パターン | 使うべき場面 | ゲームでの例 |
|---|---|---|
| ファクトリ | 生成の種類が少なく、増える見込みも少ない | 固定の敵リストから生成 |
| ファクトリメソッド | 生成するクラスの種類が今後増える見込みがある | ステージごとに異なる敵を生成 |
| アブストラクトファクトリ | 関連するオブジェクト群の組み合わせを保証したい | UIテーマ・プラットフォーム別アセット切り替え |

迷ったときは<span style ="color: red;">**ファクトリから始め、拡張の必要が生じてから上位パターンへ移行する**</span>のが現実的。  
最初からアブストラクトファクトリを設計しようとすると、  
やりすぎな設計になりやすい。  

---

## **要点**

ファクトリパターンの本質は  
<span style ="color: red;">**「`new` を呼ぶ責任を一か所に集め、呼び出し側から生成の詳細を隠す」**</span>こと。  
三つのバリエーションはその責任の持たせ方の違いにすぎず、  
目的はいずれも共通している。  

生成処理が各所に散らばり始めたと感じたとき、  
ファクトリパターンの導入を検討してみるといい。
