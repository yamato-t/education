# **コンポーネントパターン**

---

## **コンポーネントパターンとは**

コンポーネントパターンとは、オブジェクトの機能を独立した小さなクラス  
（コンポーネント）に分割し、それらを組み合わせて一つのオブジェクトを  
構成する設計パターン。  

Unity の `AddComponent` や UE5 の `UActorComponent` がまさにこの考え方。  
<span style ="color: red;">**「継承より合成」**</span>という設計原則を体現したパターン。  

---

## **なぜコンポーネントパターンが必要か**

### **深い継承階層の問題**

ゲームオブジェクトを継承で表現しようとすると、  
次のような階層になりがち。  

```
GameObject             (描画)
 ├─ Character          (移動・HP・攻撃)
 │   ├─ Player        （入力）
 │   └─ Enemy         （AI）
 │
 └─ Prop               
     ├─ StaticProp    （描画のみ）
     └─ MovableProp   （移動）
```

ここに、下記を満たした罠オブジェクトを追加する場合を考える。

- 描画する
- 移動する
- 攻撃する
- AI はない
- HP はない
- 入力は受けない

素直に考えると `Character` が一番近い。  
その為 `Character` を継承した派生クラスとして作成する。  
だがこの時、**不必要な機能まで継承で取り込んでしまう事になる**

```c++
// 罠オブジェクト
class TrapObject : public Character 
{
    // HP は不要なのに機能を継承してしまう
};
```

これだけであればまだ単純だが、  
実際のゲーム制作では多種多様な機能を持ったオブジェクトの実装が必要になる。

その実装で継承を重ねるほどクラスは肥大化し、  
大量の不要な機能まで引き継いだ**神クラス**が生まれやすくなる。  

---

## **コンポーネントパターンの仕組み**

### **二つの要素**

- <span style ="color: red;">**Component（コンポーネント）クラス**</span>
    - 「移動」「描画」「入力」「HP」など、機能単位のクラス。  
    - それぞれが独立しており、互いを知らなくてよい。  
- <span style ="color: red;">**GameObject（コンテナ）クラス**</span>
    - コンポーネントを保持するだけの入れ物。  
    - 機能の実装は持たず、各コンポーネントに処理を委譲する。  

### **構造の概要**

```
GameObject
 ├─ TransformComponent  （位置・回転・スケール）
 ├─ RenderComponent     （描画）
 ├─ InputComponent      （入力）
 └─ HealthComponent     （HP管理）
```

必要なコンポーネントだけを組み合わせることで、  
どんな性質のオブジェクトでも柔軟に表現できる。  

---

## **実装例**

### **Component 基底クラス**

まずはコンポーネントの基底クラスを用意する。  
更新と描画を行う関数のみ用意する。

```c++
class GameObject;  // 前方宣言

// コンポーネントの基底クラス
class Component {
public:
    virtual ~Component() = default;

    // 更新処理
    virtual void update(GameObject& owner) {}
    // 描画処理
    virtual void render(GameObject& owner) {}
};
```

### **具体的なコンポーネントクラス**

続いて、基底クラスを継承した具体的なコンポーネントクラスを用意する。  
例で移動、HP管理、レンダラクラスを用意。

```c++
// 移動を担うコンポーネント
class TransformComponent : public Component {
public:
    // 更新処理
    void update(GameObject& owner) override {
        // Owner に位置を反映する処理など
    }

    // 描画処理
    void render(GameObject& owner) override {
        printf("座標：(%.2f, %.2f)\n", x_, y_);
    }

public:
    // 位置を移動させる
    void move(float dx, float dy) {
        x_ += dx;
        y_ += dy;
    }

private:
    // 移動に必要な座標をメンバー変数として保持する
    float x_{}; 
    float y_{};
};

// HP 管理を担うコンポーネント
class HealthComponent : public Component {
public:
    // 描画処理
    void render(GameObject& owner) override {
        printf("体力：%d / %d\n", hp_, maxHp_);
    }

public:
    // HP を設定する
    void setMaxHp(int maxHp) {
        maxHp_ = maxHp;
        hp_    = maxHp_;
    }

    // ダメージ処理
    void damage(int damage) {
        hp_ = std::max(0, hp_ - damage);
    }

    // HP を取得する
    int getHp() const { return hp_; }

    // 死亡したかどうか
    bool isDead() const { return hp_ <= 0; }

private:
    // HP 管理に必要な情報をメンバー変数で保持する
    int hp_{};
    int maxHp_{};
};

// 描画を担うコンポーネント
class RenderComponent : public Component {
public:
    // 描画処理
    // 更新処理は行わないので、update はオーバーライドしない
    void render(GameObject& owner) override {
        printf("名前：%s\n", owner.getName().data());
    }
};
```

### **GameObject（コンテナ）クラス**

各コンポーネントを文字列をキーとしたマップで管理する。  
`addComponent()` で登録し、`getComponent()` で取り出す。  
また、登録したコンポーネントの更新処理などを一括で呼び出す。

```c++
// ゲームオブジェクトクラス
// GameObject クラス
class GameObject {
public:
    GameObject(std::string_view name)
        : name_(name) {
    }

public:
    // ゲームオブジェクトの名前を取得する
    std::string_view getName() const { return name_; }

    // コンポーネント名を指定してコンポーネントを登録する
    void addComponent(std::string_view name, Component* component) {
        components_[name.data()].reset(component);
    }

    // コンポーネント名を指定してコンポーネントを取得する
    Component* getComponent(std::string_view name) {
        auto it = components_.find(name.data());
        if (it != components_.end()) {
            return it->second.get();
        }
        return nullptr;
    }

    // 更新処理
    void update() {
        // 各コンポーネントの update を呼び出す
        for (auto& pair : components_) {
            pair.second->update(*this);
        }
    }

    // 描画処理
    void render() {
        // 各コンポーネントの render を呼び出す
        for (auto& pair : components_) {
            pair.second->render(*this);
        }
    }

private:
    std::string                                       name_;        // ゲームオブジェクトの名前
    std::map<std::string, std::unique_ptr<Component>> components_;  // コンポーネントを名前で管理するためのマップ
};
```

### **組み合わせて使う**

ゲームオブジェクト毎に登録するコンポーネントを変える。  
不必要な機能を持たせない形が可能になる。

```c++
// プレイヤー：移動・描画・HP すべてを持つ
GameObject player("Player");
player.addComponent("render", new RenderComponent());
player.addComponent("transform", new TransformComponent());
player.addComponent("health", new HealthComponent());

// 背景オブジェクト：描画だけを持つ
GameObject background("Background");
background.addComponent("render", new RenderComponent());

// 罠オブジェクト：移動と描画だけを持つ
GameObject trap("Trap");
trap.addComponent("render", new RenderComponent());
trap.addComponent("transform", new TransformComponent());

// コンポーネントへのアクセス
HealthComponent* health = static_cast<HealthComponent*>(player.getComponent("health"));
if (health != nullptr)
{
    health->setMaxHp(100);
}

// ゲームオブジェクト毎に情報を描画する
player.render();
background.render();
trap.render();
```

継承では表現しにくかった「移動するが HP を持たない」オブジェクトも、  
コンポーネントの組み合わせで自然に表現できる。

## **継承との比較**

| 比較項目 | 継承による設計 | コンポーネントパターン |
|---|---|---|
| 機能の追加 | 基底クラスの修正、または再継承が必要 | コンポーネントを追加するだけ |
| 不要な機能 | 基底クラスから引き継いでしまう | 必要なものだけを選んで持てる |
| 新種オブジェクト | 階層のどこに置くか悩む | 組み合わせで自由に表現できる |
| 実行時の変化 | 継承構造は静的で変えられない | 実行時にコンポーネントの着脱が可能 |

## **注意点**

### **コンポーネント間の依存**

コンポーネントは互いに独立しているのが理想だが、  
実際には依存してしまう事がある。  

```c++
void update(GameObject& owner) override {
    // 別のコンポーネントを owner 経由で取得するのは許容範囲
    TransformComponent* transform =
        static_cast<TransformComponent*>(owner.getComponent("transform"));

    if (transform != nullptr) { /* transform を使った処理 */ }
}
```

`getComponent()` 経由での参照は許容範囲だが、  
<span style ="color: red;">**コンポーネント同士が直接ポインタを持ち合う設計は避けた方がいい**</span>。  

### **コンポーネント数が増えすぎる場合**

機能をすべてコンポーネントに分割しようとすると、  
逆に管理が煩雑になることもある。  
「一つの責務として切り出す意味があるか」を基準にして  
粒度を判断すると良い。  

---

## **まとめ**

| ポイント | 内容 |
|---|---|
| 目的 | 機能を独立したコンポーネントに分割し、組み合わせで表現する |
| 解決する問題 | 深い継承階層・神クラスの肥大化 |
| 主な用途 | ゲームオブジェクトの機能管理（Unity・UE5 の設計思想） |
| 設計原則 | 継承より合成（Composition over Inheritance） |

コンポーネントパターンの本質は、  
<span style ="color: red;">**「何者であるか（is-a）ではなく、何を持つか（has-a）で設計する」**</span>こと。  
継承で表現しようとして行き詰まったとき、  
特に「必要ない機能まで大量に継承してしまいそう」となった時、  
コンポーネントへの切り替えを検討してみるといい。
